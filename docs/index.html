ModelDB  ·  two products

Encrypted storage for the app in your pocket and the server behind it.

ModelDB is two separate products that share an idea, not code. One lives inside a mobile or wearable app and keeps its data sealed on the device. The other is a server you run: it stores AI models, documents and tables, and you work with them in plain sentences. Pick one, or use both.

mdc-lite

An encrypted key-value store that disappears into your app

Five functions linked into your binary. Every value and every key name is sealed before it touches disk, then written as DNA-style A/C/G/T text. No server, no network.

Is either one's data actually stored as a DNA molecule?No. Both encode data as A/C/G/T text — mdc-lite in its on-disk files, MDC Platform in its archive tier — but it's always encrypted first, then represented as base-letter characters in an ordinary file or database. A software simulation, not a physical molecule. No synthesis, no sequencing, no wet lab, anywhere in either codebase.
Against a traditional databaseMDC Platform is not a faster or smaller database. Measured on the same 10,000 records it used about 2.7 times PostgreSQL's disk space, inserted about 20 times slower than PostgreSQL, and looked records up in about a second because it has no indexes (so lookups grow with the table). What you get instead is no SQL, no drivers and no managed instance to run: for a small always-on app, about $5 a month on a usage-billed host against about $14 for the smallest Amazon RDS PostgreSQL instance, with RDS's backups and failover not included in that gap. mdc-lite

A key-value store built for the places a server can't reach: a watch face, a phone app, a background service. Every value and every key name is sealed under XChaCha20-Poly1305 before it ever touches disk. No runtime, nothing readable outside the app that wrote it.

What it does

Encryption

Sealed keys, not just sealed values

Key names are hashed with a keyed BLAKE3 hash before they ever become a filename — a directory listing of the raw store reveals nothing, not even how your data is organized.

Custody

The key is yours, on purpose

This library takes a 32-byte key and never generates, stores, or touches it beyond that. Real custody belongs to the platform's own secure hardware — iOS Secure Enclave / Keychain, Android Keystore / StrongBox — which is exactly where it should live.

Footprint

348 KB, stripped, zero runtime

Built in Rust with opt-level = "z", LTO, and symbols stripped. No garbage collector, no interpreter, no background thread — a handful of file reads and writes, nothing more.

Integrity

Two failure modes, chosen on purpose

get() on a specific key fails loud if it's been tampered with. list_keys() quietly skips anything it can't decrypt, so one bad or foreign file never hides every other valid key in the store.

Interop

A C ABI, not a Rust-only API

Every operation is exposed through a five-function C header — bind it from Swift, Kotlin, or anything else that speaks C calling conventions. No wrapper generation, no FFI framework.

DNA-encoded storage

The file on disk is ACGT text, not binary

Every encrypted entry is DNA-encoded (2 bits per base — 00→A 01→C 10→G 11→T) before it's written, the same encoding MDC Platform's archive tier uses. It's ciphertext under the base letters, never plaintext — the mapping is public, encryption is what actually protects it.

Five functions. That's the whole API.

use mdc_lite::LiteStore;

let key: [u8; 32] = /* from platform secure storage */;
let store = LiteStore::open("/path/to/store", key)?;

store.put("diary/2026-08-24", b"...")?;
let value = store.get("diary/2026-08-24")?;
store.exists("diary/2026-08-24");  // bool
store.delete("diary/2026-08-24")?;
let all_keys = store.list_keys()?;  // Vec<String>
#include "mdc_lite.h"

MdcLiteStore *store = mdc_lite_open("/path/to/store", key);

mdc_lite_put(store, "diary/2026-08-24", data, data_len);

uint8_t *out; size_t out_len;
mdc_lite_get(store, "diary/2026-08-24", &out, &out_len);
// ... use out[0..out_len) ...
mdc_lite_free_buffer(out, out_len);

mdc_lite_close(store);
// via the C header, bridged into Swift
let store = mdc_lite_open("/path/to/store", keyPtr)

mdc_lite_put(store, "diary/2026-08-24", valuePtr, valueLen)

What it does

Plain sentences

Ask, don't query

Create, read, update, delete and analyse by asking. Ambiguous words are clarified, deletes are confirmed, and no sentence ever becomes SQL — a deterministic validator, not the language model, decides what reaches storage. Read more →

Object store

Any bytes, classified by content

AI models, images, documents, logs, tensors and tables are recognised from their content (not the filename) and tiered HOT / WARM / COLD / ARCHIVE. Read more →

AI models

One layer, not the whole checkpoint

A .safetensors file is parsed and every tensor stored and tiered on its own, so you can fetch a single layer without reading the rest. Read more →

DNA-inspired archive

Encrypted first, then A/C/G/T

The ARCHIVE tier seals data with AES-256-GCM, then writes it as base letters, with error correction and a corruption simulator. A software simulation — no physical DNA. Read more →

Databases and search

Unlimited, isolated, searchable

Create as many databases as you like, add typed tables, insert and browse — and find across every database and document at once. Read more →

Import

Bring a design, a CSV, a script

Attach a Markdown design document, CSV, SQL script, ER diagram or an MDC export. A SQL script is parsed, never run; nothing is written unless the whole file is valid, and nothing is overwritten. Read more →

Export

Take it out in the format you need

CSV, SQL, Excel, a design document with an ER diagram, or an MDC export file another instance can import. Exports are plain files — the sealing protects data inside MDC, not what you download. Read more →

Schema design

Describe the tables, confirm, done

Say create database shop with customers(name, email), orders(total decimal) or paste an ER diagram. MDC shows the design and creates it only when you reply yes. Read more →

Agent state streams

Event sourcing, rebuilt as of any time

An AI agent's state kept as a base plus timestamped events instead of an overwritten value, then rebuilt exactly as it was at any moment (model weights stay in the object store). Every record, including its times, is sealed per stream; a tampered or missing event is detected. Read more →

Deleting

Permanent, so it asks first

Drop a database or table, delete a row or stream. MDC says what would be lost and waits — a database needs its name typed — and anything but a yes cancels. The default database is protected. Read more →

Storage Explorer

A browser app with a chat panel

Browse by type, tier or database; preview, archive or delete objects; and chat — import with a paperclip, export with a download button. Read more →

API and access

Bearer tokens and four roles

A REST API for your own UI or NLU (RASA included): every route needs a token, and its role — viewer, editor, db_admin, admin — decides what it may do. Read more →

Monitoring

A port that keeps publishing

An optional second port serves CPU, memory and per-database statistics as Prometheus metrics, JSON and a live event stream, and can publish the same snapshots to Kafka for a dashboard or monitoring system. Read-only, off until you turn it on. Read more →

Deployment

Docker and Railway

A Dockerfile and Railway config with a health check and a persistent volume; the deployed Explorer asks for the API token. Read more →

Run it

You need Python. This starts the browser app (Storage Explorer) and the REST API on your own machine; Installation has the rest, and Deployment covers Docker and Railway.

# get it
git clone https://github.com/saji1970/ModelDB.git
cd ModelDB/mdc
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# the browser app and REST API at http://127.0.0.1:8000
python -m mdc serve

# or the conversational shell
python -m mdc

# an API token for your own app or NLU
python -m mdc token issue my-integration --role editor

Then ask it things: create database shop with customers(name, email), list models, find widget under 20000, create stream agent-1 with mood=calm. Every chat command →

On "quantum encryption"

BOTH PRODUCTS
WHAT IT ISN'T

Real QKD needs a fiber link

Quantum key distribution transmits photons between two fixed physical endpoints over dedicated hardware. It's a network-link technology — there's no version of it that runs inside an app on a phone or a watch.

WHAT IT IS

256-bit symmetric, already enough

Grover's algorithm only halves a symmetric key's effective strength — 256 bits stays enormous. Quantum computers threaten asymmetric crypto (RSA/ECC) instead, which neither product uses to protect data.

A DIFFERENT QUESTION

Can data itself be "stored as a quantum state"?

No — verified, not assumed. A qubit's superposition decoheres to a fixed, data-independent state in a handful of T2 lifetimes even with nobody reading it, confirmed by solving the Lindblad master equation in QuTiP against its exact analytic solution. There's no hardware today that holds a quantum state at rest the way a disk holds bits. Full derivation →
